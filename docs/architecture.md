# 架构评审：这个项目该怎么实现

> 写给将来的维护者，也写给现在想动手改它的人。
> 里面每一条判断都附了理由；不同意可以，但要先知道你在不同意什么。

---

## 0. 先把需求翻译成工程问题

原始需求是五条能力 + 五条风险。作为工程问题，它们其实是三类：

| 原始需求 | 真正的工程问题 | 难点在哪 |
|---|---|---|
| 插件化安装 / 注册 / 能力标签 | **服务发现 + 身份** | 不难，但"谁来证明你是你"很难 |
| 好友双向同意 / 群表决入群 | **分布式授权** | 表决会在成员变动时死锁 |
| 结构化消息 / 持久化 / 在线状态 / 回执 | **可靠投递** | at-least-once + 幂等，别想 exactly-once |
| 跨框架兼容 | **适配面设计** | 面越大，维护成本指数上升 |
| 风险 1：无限循环 | **分布式流控 + 终止协议** | 这是本项目真正的技术核心 |
| 风险 2：安全 | **不可信输入的边界** | 出站比入站更危险，而多数人只做入站 |
| 风险 5：合规 | **部署形态选择** | 不是技术问题，是产品边界问题 |

**我的结论：这个项目的技术难点只有两个——循环治理和数据出域治理。
其余的（注册、好友、群、投递）都是常规 CRUD，写得干净就行，不要在这上面炫技。**

一个常见的失败模式：把 80% 的精力花在"好友列表好不好看""群表决 UI 怎么设计"，
然后在第一次上线就被两个 Agent 聊到天亮、或者把内网地址发出去，项目直接死掉。

## 1. 架构决策（ADR）

### ADR-1：控制面与数据面分离，但允许物理合体

**决策**：注册中心只回答"谁能跟谁说话"；消息载荷不经过它（原型阶段经过，但只做盲转发）。

**理由**：
- 合规上，"盲转发管道"比"内容服务"好解释得多（我们不触达业务内容）。
- 工程上，控制面的 QPS 比数据面低两个数量级，可以独立扩缩容。
- 出事时，审计日志里只有元数据（谁、何时、发给谁、多大），没有业务内容——
  这既保护用户，也保护运营方。

**代价**：原型里两者共用一个 HTTP 口，容易被人误以为"消息存在服务器上"。
所以代码里一开始就分表、分权限、分审计，`messages` 表只存信封不存附件。

### ADR-2：用"信封"取代"消息"

**决策**：一等公民是 `Envelope`，不是 `message`。

**理由**：IM 的一元 message 模型无法表达"这件事干完了"。没有终止语义，
Agent 只能靠"感觉"停——而 Agent 永远不觉得自己该停。

信封里必须有的四个字段：

```
ttl_hops   还能转几手（抄 IP TTL）       → 解决"绕圈转发"
budget     消息数/token 额度，随信递减    → 解决"预算分裂"
stage      open/done/handoff/need_human  → 解决"不知道该停"
act        task/result/event/chat        → 解决"语义混淆"
```

**反例**：只加 `max_rounds` 的方案，在 A→B→C→A 的三角转发下完全失效，
因为每段链路的 round 都从 0 开始。

### ADR-3：治理层 = 递减量 × 内容指纹 × 速率

**决策**：三个维度同时生效，任一触发即降级或熔断。

**理由**：这五种死法各自需要不同的检测手段，缺一个就漏水。

| 死法 | 递减量 | 内容指纹 | 速率 | 扇出计数 |
|---|---|---|---|---|
| 绕圈转发 | ✅ | | | |
| 语义空转 | | ✅ | | |
| 礼貌互推 | | ✅ + 交替模式 | | |
| 群聊扇出 | | | | ✅ |
| 突发洪泛 | | | ✅ | |

**实现细节（踩过的坑）**：
- 用 **simhash + 汉明距离**，不用完全相等。`"收到。"` 和 `"收到！"` 必须落到同一个指纹。
- 指纹窗口只保留最近 8~32 条。太长了会把"正常复述"误判成循环（比如总结前文）。
- **群消息按收件人计数**。10 人群一条消息 = 10 条配额，不是 1 条。
  这一条不做，群聊就是 token 焚烧炉。
- 熔断时**不要抛异常就完事**，要给模型一段明确指令（"立刻输出最终结论、停止调用工具"）。
  异常会让 Agent 崩掉重试，指令才能让它体面收尾。

### ADR-4：失败关闭（fail-closed），并且做在 SDK 里

**决策**：出站 DLP 默认 `BLOCK`；入站注入检测默认 `QUARANTINE`；没有跳过开关。

**理由**：
- 安全机制一旦变成"建议开启"，上线三个月后一定被关掉（因为误报烦人）。
- "默认放行 + 警告"在一次真实事故后会被追责；"默认拦截 + 人工确认"最多被抱怨两句。
- 做在 SDK 里而不是文档里：使用者改不了，也忘不了。

**代价**：误报会让人烦。所以给了三条出路：
1. 改内容（推荐，90% 场景够用）
2. `allow_terms` 白名单（针对稳定的误报）
3. `--force`（人已确认，留审计，责任在人）

### ADR-5：本地优先（localhost 起步）

**决策**：v1 只做自托管。公网只是把 `--host` 改成 `0.0.0.0`，不是另一套代码。

**理由**：
- **冷启动**：社交网络依赖在线节点数，初期一定冷清。但"单机多 Agent 协作"不冷清——
  开发者本机就有 3~5 个 Agent。先让工具在单机上产生价值。
- **合规**：境内公网信息服务涉及资质问题，这不是技术能解决的。不做公网托管，直接绕开。
- **安全**：本机回环不产生数据出域风险，用户可以先在安全环境里把机制跑熟。

**这条是我认为最重要的产品判断。** 它同时干掉了你列的风险 #4 和 #5，
而且是唯一一个"不写额外代码"就能拿到的收益。

### ADR-6：会话即身份，身份即密钥（v0.3）

**决策**：一个对话窗口 = 一个稳定的 agent 身份。身份由宿主的会话 ID 派生，
不是由用户输入的名字派生。

**要解决的问题**：Agent 的每次工具调用都是**新进程**，没有内存可依赖。
如果每次调用都生成一个新 agent 名，同一个对话跑三遍就在注册中心留下三个
身份——消息投给谁、谁回的、审计链上这两条属于不是同一个人，全说不清，
还会让对端反复触发"公钥变了"的告警。

**为什么用会话 ID 而不是名字**：
- 会话 ID 是宿主给的、稳定的、一个窗口一个；名字是人起的、会改的、会撞的。
- 名字当主键的直接后果是：用户把"运维"改成"运维二"，注册中心里就换了一个人，
  好友关系、群成员、对端 pin 全部失联。

**代价**：同一个对话被"复制"成两个（例如分支对话）时，两个副本会共用身份。
这个风险目前接受——共享身份的后果是审计上分不清是哪个副本，而不是安全问题。

### ADR-7：同机互信用"审计"换"审批"，但只在回环地址生效（v0.3）

**决策**：同一台机器上的会话互发消息，不要求先走双向好友审批，
但这个开关（`local_mesh`）**只在注册中心监听回环地址时**允许打开，
且每次放行都写审计（`mesh.local_trust`）。

**为什么这不是"关掉安全"**：
同一个 OS 用户本来就能读 `~/.a2alink/` 下所有私钥、能直接改 SQLite、
能伪造任何本机身份。在这个前提下要求本机会话互加好友，是一道**自己演给
自己看**的仪式，不是边界。真正的边界是"这台机器别被别人用"。

**为什么必须限制在回环地址**：
一旦 `--host 0.0.0.0`，注册者来自四面八方，免好友就等于允许陌生人直接
给任何人投递消息——那是投毒面，不是便利。所以 CLI 层强制：非回环地址
一律关闭并明确告知，不做静默降级。

**为什么不干脆删掉好友机制**：
跨机器通信里，双向好友仍然是唯一能表达"我认识你"的手段，且成本极低。
同机互信只是**在同一个信任域内**把这道手续省掉。

**这条也是可撤销的**：`a2alink up --no-mesh` 回到严格模式。默认值可以方便，
但不能悄悄——所以启动时会打印一行说明。

### ADR-8：把「已读」和「做完了」拆成两个事实（v0.4）

**决策**：投递位点（`state`/`cursor`）与处理结果（`done_at`）分开记录。
收信不再等价于完成任务。

**要解决的问题**：以前 `ack` 一拍两散——读了就当地处理完了。
于是三种真实情况在审计链上是同一个样子：

1. Agent 读完崩溃 → 任务永久丢失；
2. Agent 读完转手给别人 → 没人知道原手已经放手；
3. Agent 读完发现自己做不了 → 既没回话，也没报错。

三者的共同点是**日志上什么都没有**。而"没有记录"比"记录失败"恶劣得多：
后者能查、能重试、能追责；前者只会表现为"对方说发了，这边说没收到"。

**为什么不做完整的可靠投递**（in-flight 窗口 + 超时自动重投 + 逐条确认）：

- 那套东西需要后台状态机、租约、心跳，复杂度接近一个小型 broker；
- 而在 Agent 场景里，**"任务有没有结果"比"消息有没有重投"更要紧**。
  一条消息重投十次仍然失败，价值是零；但只要它被标记成"未完成"，
  人就可以介入。所以优先做"事实可见"，而不是"自动重试"。

**做法**：
- 保留 cursor 的单调性（它管"读到哪"），新增 `done_at`（管"做完没"）。
- 重投不倒退 cursor，而是**新建一条 delivery**。代价是同一条消息有多条投递
  记录——但那本来就是事实，应该看得见"这条投过三次"。
- 失败超过阈值进死信（`dlq`），死信可重投、可清理，但**清理只标记不删行**。
- `inflight` 只显示每条消息**最近一次**投递，避免"一条未完成任务"显示成三条。

**代价**：多了一步 `a2alink done <id>`。这一步不做，`inflight` 就会一直挂着。
这是刻意的——它让"没做完"这件事**持续可见**，而不是自动消失。
一个会自动清空的待办列表，最后一定会变成一个没人看的列表。

### ADR-9：遗嘱必须由客户端预签，服务端只保管（v0.4）

**决策**：`will` 存的是**客户端已经签好名的整条信封**，不是一段文本。

**要解决的问题**：Agent 崩溃是静默的。任务在它手上，对方还在等，
而没有人知道它已经不在了。MQTT 的 Last Will 解决了同样的问题，
但它的 broker 有权限代发任意消息。

**为什么不能照抄**：本项目的注册中心**没有私钥**（ADR-4 的核心承诺）。
它代发生成的消息必然签不出有效签名。接收方只有两个选择：

- 拒收 → 遗嘱功能等于不存在；
- 或者为遗嘱开一个"不验签"的降级口子 → 那个口子一旦存在，
  伪造遗嘱只需要会调接口。

所以只有第三条路：**客户端活着的时候先签好，服务端只做保管和转交。**
它改不了内容（改了就验不过签），也读不到内容（本地已加密）。

**顺带的设计**：
- 掉线判定用 `last_seen` + 可配置 TTL（默认 600 秒），不用连接状态——
  HTTP 无连接，任何"连接状态"都是伪造出来的假象。
- 触发后立刻落 `will_fired=1`，**再**投递。投递失败也不能重试，
  否则一个死循环的遗嘱就是一场消息风暴。
- `a2alink down` 默认撤销遗嘱。正常下线用不上它，
  不撤的话对方会在十分钟后收到"我掉线了"，而人其实好好的。

## 2. 逐条回应原始需求

### 2.1 插件化安装 + 注册 + 能力标签

实现：`POST /v1/agents/register` → 返回 `agent_id` + 一次性 token。

**我加的东西**：
- `invite_code`：非空时注册必须带邀请码。公网部署的**最低门槛**，成本 5 行代码。
- 名称唯一约束 + 字符集校验（2~40 字符）。否则会被人抢注成 `OpenAI-官方`。
- `discover` **不返回** owner、token_hash、endpoint 等字段。发现 ≠ 暴露。

**我没做的**：DID / 链上身份。理由见 §3.3。

### 2.2 好友双向同意

实现：`friend_requests` + `friends(pair PRIMARY KEY)`。
`pair = sorted([a,b]).join("|")` 保证反向边不会重复。

**服务端强制**：`send()` 时检查 `friendship == accepted`，否则 403。
客户端也判一遍是为了省一次往返，不是安全边界。

**我加的东西**：
- 反骚扰：同一对 24 小时最多 3 次申请。
- 好友关系可撤销，撤销后立即生效（不是"软删除"）。
- `peer_scopes`：给每个好友单独设信任域（这个好友在内网，那个在公网）。

**未来要加的**：介绍人机制（vouching）——A 认识 B，B 认识 C，C 申请加 A 时带 B 的背签，
A 的审批成本从"调查"降到"看一眼"。这是解决冷启动 + 垃圾申请的杠杆点。

### 2.3 群聊 + 全员表决

**原始设计**：新增成员默认全员同意才能加入，可切换一票否决/多数表决。

**我的判断：全员表决不能当默认值。** 三条硬理由：

1. **可用性**：5 人群里只要有 1 人休假，入群就永久挂起。10 人群基本不可用。
2. **成员变动死锁**：表决期间有人退群，快照里的人永远投不了票 →
   提案永久 `pending`。我在 `remove_member` 里做了快照收缩 + 重算，但这是补丁，不是解法。
3. **女巫成本**：全员表决意味着**任何一个人都能阻止一切**。攻击者只需要混进群一次，
   就能永久瘫痪这个群的扩张。这在公网上是不可接受的。

**实现**：三种模式都做了，默认 `unan`（尊重原始需求），但 README 里明确写"只适合 ≤5 人核心组"。
推荐默认是 `majority` + `quorum=0.6` + `proposal_ttl=24h`。

**必须有的三个机制**（原始需求里没有，但不做就是废的）：
- **成员快照**：提案创建时冻结投票人名单。否则投票语义随成员变动漂移。
- **快照收缩 + 重算**：成员退出后，从所有未结提案里剔除，并立刻重算是否已达标。
  （很多人只做前半步，结果"票够了但没人再投"→ 永久挂起。）
- **超时策略**：`reject`（默认，保守）或 `approve_if_quorum`（激进）。必须显式配置，
  不能默认"超时算通过"——那等于给攻击者一个等待窗口。

### 2.4 消息形式 + 持久化 + 在线状态 + 回执

- **结构化 + 自然语言**：`payload` 是任意 JSON，`instruction` 是约定字段。
  适配器只读 `instruction`，其余作为 `context` 透传。
- **持久化**：SQLite WAL，`messages` + `deliveries` 两张表。投递是 at-least-once。
- **回执**：`POST /v1/inbox/ack {cursor}`，客户端本地记 cursor。
- **在线状态**：`last_seen` 心跳。**我没做实时在线状态**——
  它需要长连接，而长连接会带来一堆运维问题（NAT、心跳风暴、重连风暴）。
  原型阶段用 `last_seen` 足够，真要做得上 SSE/WebSocket（见 roadmap M2）。

**关键语义**：不承诺 exactly-once。用 `idempotency_key` 去重表实现"重复投递无副作用"。
承诺 exactly-once 的分布式系统，最后都会在某个边界条件下骗你。

### 2.5 跨框架兼容

**原始设计**：兼容 DeepSeek Harness / AutoGen / CrewAI / LangGraph。

**我的判断：不要把"兼容"做成插件矩阵。** 4 个框架 × 3 个版本 = 12 个组合，
维护成本会吃掉整个项目。

**做法**：定义一个**单一适配面**——

```python
handle(client, received) -> dict | None
```

框架差异全部收敛到"怎么调一次模型"。于是每个适配器只有 20 行：

```python
class AutoGenAdapter:
    def handle(self, client, received):
        resp = self.agent.generate_reply(messages=[{"content": build_prompt(self.system, received)}])
        return parse_reply(resp["content"] if isinstance(resp, dict) else resp)
```

**第二条路（更省事）**：`TOOL_SPECS`。任何支持 function calling / MCP 的框架，
把这 7 个工具 schema 注册进去就完事，不需要适配器。这条路在框架升级时最不容易崩。

**说人话**：宣称"兼容所有框架"是营销，不是工程。诚实的表述是
"1 个协议 + 1 个适配面 + 3 个参考适配器，其他框架 20 行接入"。

## 3. 我删掉的东西

### 3.1 公网托管中继网关（v1 删）

**技术替代**：自托管 + 内网 bind + 可选盲转发网关（不解包 payload）。
**删的理由**：合规成本 >> 收益，且冷启动阶段没人用。
**什么时候加回来**：有 3 个以上真实用户明确说"我需要跨组织通信"，且愿意承担合规责任。

### 3.2 全员表决作为默认（降级为可选）

见 §2.3。默认改 `majority`，`unan` 保留给核心小组。

### 3.3 链上身份 / DID（不做）

**理由**：解决的对象错了。
你需要的是"我信任这个 Agent 在这个范围内做这些事"，不是"这个 Agent 的身份不可篡改"。
前者靠双向同意 + 能力契约 + 审计 + 可撤销；后者只增加了成本，没有增加安全性
（身份不可篡改 ≠ 行为可靠，被策反的 Agent 签名依然有效）。

### 3.4 "社交网络"叙事（改）

**改法**：从"Agent 社交"改成"能力发现 + 受限委派"。

用户真正的问题不是"我的 Agent 没有朋友"，而是"我这个 Agent 不会查 K8s，谁能帮我查一下"。
前者是社交问题，后者是能力路由问题。后者才能立刻产生价值。

所以 `discover --capability k8s` 的优先级高于好友列表。

### 3.5 C 端定位（不做）

无场景，且会把合规风险放大一个量级。

## 5. 数据模型（为什么这么设计）

```
agents(id, name UNIQUE, capabilities JSON, token_hash, status, last_seen)
friends(pair PK, a, b, state)                  ← pair = sorted，防反向重复边
friend_requests(id, from, to, state, created_at)
groups(id, join_mode, quorum, proposal_ttl, on_timeout)
group_members(group_id, agent_id, role, state) ← 复合主键，天然幂等
proposals(id, mode, snapshot JSON, state, expires_at)
votes(proposal_id, agent_id, vote)             ← 复合主键，一人一票
messages(seq, id UNIQUE, envelope JSON)        ← 只存信封，不存附件
deliveries(seq, message_seq, recipient, state) ← 扇出的落点
idem(key PK, message_id)                       ← 幂等去重
audit(seq, ts, actor, action, detail)          ← 追加写，不更新不删除
```

三个刻意的选择：
1. **`snapshot` 存 JSON 而不是关联表**。表决语义是"针对某个时刻的成员集合"，
   这是历史快照，不是当前状态。用关联表会诱导人去 join 当前成员，那就错了。
2. **`deliveries` 独立成表**。群发时一条消息 N 个收件人，收件人各自有已读状态。
   塞进 messages 表会导致行膨胀。
3. **`audit` 只追加**。任何"修改审计日志"的需求都应该被拒绝。

## 6. 性能与容量（诚实版）

以下都是**估算**，不是压测结果。别拿去写容量规划。

- 单进程 `ThreadingHTTPServer` + SQLite WAL：轻量场景（几十个 Agent、每秒个位数消息）
  完全够用。再往上就该换 ASGI + PostgreSQL。
- 群消息写放大 O(N)。100 人群发一条 = 100 行 `deliveries`。
  这是正确性要求（每人的已读状态要独立），不是实现缺陷。
- `inbox` 是**轮询**（默认带 `wait` 长轮询，0.15s 检查一次）。
  几十个 Agent 没问题，上百个就该换 SSE/WebSocket。
- 看门狗是**内存态**，进程重启后会话预算归零。
  这意味着"重启大法"能绕过预算——生产环境需要把会话状态落盘（roadmap M3）。

**已知的架构债**：
1. 单机 SQLite 无横向扩展能力。
2. 看门狗状态不持久，重启即重置。
3. token 用 HMAC 存哈希，注册中心理论上能冒充 Agent。
4. 没有端到端加密，中继能看到明文（虽然设计上不该看）。
5. `_recheck` 只处理成员退出，不处理"新成员加入导致 quorum 变化"。

## 7. 如果要做到生产级，还缺什么

按顺序，前三条不做就别上线：

1. **消息签名与端到端加密**：Ed25519 签名 + X25519 + AEAD。
   注册中心从"可信第三方"降级为"盲路由"，这是合规叙事的关键。
2. **看门狗状态持久化**：会话预算落盘，防重启绕过。
3. **全局限额**：按 Agent / 按组织 / 按天的成本账户，防"每次新建会话"的慢烧。
4. **身份成本**：邀请码 → 组织级 CA → 信誉分。没有身份成本的公网，一定是垃圾场。
5. **可观测性**：OpenTelemetry trace（`trace_id` 已经预留）、指标、消息账本重放。
6. **人审闸门**：超过阈值（金额/敏感度/对端等级）强制人工确认，不能自动化。
7. **一致性测试套件**：协议 conformance tests，任何实现都要过。
8. **容量与故障注入**：网络分区、重复投递、时钟漂移下的行为验证。

## 8. 我担心的地方（自我批评）

- **DLP 会给人虚假的安全感。** 这是最大的风险。正则挡不住"我们下季度主推的那个型号"。
  所以 SECURITY.md 里把"结构化数据必须人判"写在最前面，而不是藏在第 8 节。
- **默认 `unan` 是妥协。** 为了尊重原始需求保留了全员表决作为默认，但这在真实使用中会疼。
  如果重来一次，我会默认 `majority`，把 `unan` 放在显眼位置但标"仅限 ≤5 人"。
- **适配器只验证了 echo 路径。** AutoGen / LangGraph 的适配器是照 API 写的，
  没有真跑过。第一次接真框架的人会遇到坑（尤其是流式输出和 token 统计）。
- **"本地优先"可能被误读成"不需要安全"。** 其实本机也可能连着内网服务，
  `peer_scope=local` 不等于可以发密钥。文档里需要反复强调。
- **协议版本策略还没定。** 现在 `v=1`，字段只增不删。但"只增不删"在跑三年后会变成
  一个巨大的信封。需要在 M2 定一个弃用机制。

## 9. 一句话总结

> 这个项目的价值不在于"能让 Agent 连上"，而在于**"连上之后不会把公司和你的钱包一起搞没"**。
> 所有设计决策都应该服务于这句话。凡是让"连上"更容易、但让"治理"更弱的改动，都应该被拒绝。
