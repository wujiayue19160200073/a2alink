# 版本规划

这份文档回答三个问题：**现在是什么版本、下一个版本有什么、什么变更算破坏性**。

---

## 1. 版本号规则

采用 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/)，但加两条本项目专属约定：

```
MAJOR.MINOR.PATCH
  │     │     └── 修 bug、补测试、改文档、调阈值默认值
  │     └──────── 新增能力（向后兼容）
  └────────────── 协议或 API 破坏性变更
```

**专属约定 A：`0.x` 期间 MINOR 可以破坏兼容。**
学界/工程界的惯例是"0.x 随便变"，我们明确写下来，免得住后有人拿 `0.1` 的
信封去撞 `0.2` 的注册中心然后发 issue 骂人。

**专属约定 B：`1.0.0` 之后信封格式（`Envelope` 的必填字段与语义）冻结。**
冻结后的演进只能靠：
- 新增**可选**字段（旧端忽略即可）；
- `PROTOCOL_VERSION` 升整数，服务端同时支持 N 和 N-1 两个版本，给一个 MINOR
  周期的过渡期。

**专属约定 C：`0.1.x` 是"补丁列车"。**
语义修正、安全修补、文档补齐都走 PATCH，**不新增功能**。这条是为了让早期
使用者能"无痛跟进"——修安全问题的版本不应该顺带改行为。

## 3. v0.2.0 为什么是"可视化"而不是"端到端加密"

按直觉，安全功能应该优先。但这里把可视化排在前面，理由有三条：

1. **Agent 之间聊了什么，现在没人看得见。** 这是当前最大的可用性缺口——
   出了问题（循环、误发、泄密）只能翻 sqlite3 里的原始 JSON。
   看不见的东西没法治理。
2. **它同时也是最好的调试工具。** 用户接入适配器时最常见的抱怨是"我的 Agent
   到底发了什么"，一个面板直接省掉一半支持成本。
3. **加密是"加一层"的事，随时能加；可视化是"改数据流"的事，越晚做越贵。**
   要先有本地事件流（spool），才谈得上面板；先做面板，v0.3 加加密时事件流已经
   稳定了。

详见 [`docs/visual-console.md`](visual-console.md)。

## 4. 什么变更算破坏性（Breaking）

以下任一项变更是 **MAJOR**（`1.0` 后）/ **MINOR**（`0.x` 期间）：

| 变更 | 为什么算破坏性 |
|---|---|
| `Envelope` 必填字段增删改 | 老客户端会被协议层直接拒 |
| `Envelope` 字段语义变化（如 `ttl_hops` 改成"跳数"而非"剩余跳数"） | 静默出错，最难排查 |
| `/v1/*` 路由删除或改签名 | 客户端直接 404 |
| 错误码 `code` 变更 | 客户端按 code 分支，改了就断 |
| 默认安全策略收紧（如默认 `peer_scope` 从 `wan` 改成 `lan`） | 行为变了，用户无感知 |
| 群准入状态机新增必经状态 | 依赖 `state` 枚举的客户端会挂 |
| 移除 `PropagationGuard` 的默认开启 | 安全默认值退化 |

以下**不算**破坏性：

- 新增可选字段 / 新增路由 / 新增命令；
- 阈值调优（除非跨越数量级）；
- 内部模块拆分。

`0.1.0 → 0.1.1` 里的 `state` 新增 `pending_consent` **算破坏性**，
但因为处于 `0.1.x` 补丁列车且是修安全语义，我们选择**在小版本内做**，
并在 `CHANGELOG.md` 明确写"调用方必须适配"。这是一个**有意识的例外**，
写在这里是为了以后有人问"你们不是说 0.1.x 不改行为吗"。

## 5. 弃用流程

1. 在 `CHANGELOG.md` 的 `Deprecated` 段落登记；
2. 代码里打 `DeprecationWarning`，至少保留 **一个 MINOR** 周期；
3. 文档里标注"将在 vX.Y 移除"；
4. 到点才删。

对 `0.x` 期间的破坏性变更，同样走上面四步，**但周期可以缩短到一个 PATCH**
（因为用户基数还小）。

---

## 6. 分支与标签

```
main         始终可发布；每次 PATCH 直接提交
v0.1.1       每个发布打轻量标签，不建长期维护分支
hotfix/x.y.z 仅在已发布版本出现安全问题时临时开，修完合并回 main
```

`1.0` 之后会开 `release/1.x` 维护分支，`0.x` 期间不开——**早期不做多分支维护，
因为维护成本会吃掉全部开发时间**。

---

## 7. 版本号放在哪

| 位置 | 说明 |
|---|---|
| `pyproject.toml` → `version` | 打包与 `pip` 用 |
| `src/a2alink/__init__.py` → `__version__` | 运行时 `a2alink --version` 用 |
| `CHANGELOG.md` | 人读的变更记录（唯一权威） |

这三处必须同步。**没有自动同步脚本是刻意的**：发版时手动改三个地方，
会强制发版人重新看一眼 CHANGELOG 有没有写。

---

## 8. 兼容性承诺（对使用者）

- `0.x`：不承诺向后兼容，但**每次破坏性变更都会写进 CHANGELOG 的 `Changed` 段，
  并说明怎么改**。
- `1.x`：承诺信封与 API 向后兼容；破坏性变更只出现在 `2.0`。
- 安全修补永远**优先于**兼容性：如果某个兼容性和一个正在被利用的漏洞冲突，
  我们修漏洞，并在 CHANGELOG 里标 `SECURITY`。
