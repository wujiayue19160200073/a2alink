# 寻址：怎么找到"对的那个对话"

> 这份文档回答一类具体问题：
> "我有五个对话窗口，A 想找做数据库的那个，它怎么知道是哪一个？"
> "两个 Agent 各有好几个对话，中间怎么对上号？"
> "能不能让 B 开一个新对话去干活？"

---

## 一、先划清一条物理边界

**a2alink 不能让另一个 Agent 新开对话。**

这不是没做，是做不到，而且不应该假装做到：

- 技能（Skill）是被**调用**才执行的代码，不是常驻进程。A 的进程里没有任何
  句柄能创建 B 的窗口、会话或上下文。
- 真实存在的"帮我开个对话"只有一条路：调用宿主的私有接口。那种东西今天能跑，
  宿主升个版本就碎，还会让使用者误以为"任务一定被接手了"——而实际上消息
  只是躺在一个没人打开过的窗口里。
- 更根本的问题：**新开的对话没有身份、没有历史、不知道自己要干什么**。
  就算能开，你也不知道它会不会理解任务，而"开了但理解错了"比"没开"更难查。

**能做的替代方案，按可靠性排序：**

| 做法 | 谁发起 | 可靠性 | 适用 |
|---|---|---|---|
| 投递到目标 Agent 已有的某个会话，等它下次被唤起 | 发送方 | 高（消息不会丢） | 默认做法 |
| 目标侧常驻一个轮询进程（`a2alink check` 循环） | 接收方自己 | 中（要有人维护进程） | 需要较快响应 |
| 由人在目标侧手动开对话，然后 `check` | 人 | 高但要人参与 | 低频率、高价值任务 |

所以本项目的正确用法是：**"把任务放进对方的信箱，并接受它可能几小时后才被读到"**。
`ask` 的超时是如实告知，不是重试循环——那正是死循环的来源。

---

## 二、一个会话 = 一个身份

这是整个寻址模型的地基，必须先说清，否则后面全错。

```
一个对话窗口（宿主给一个会话 ID）
        ↓  派生（不可变）
一个协议身份 agent_name = s-<会话ID前缀>
        ↓  一个
一套密钥 / 一条审计链 / 一个收件箱
```

推论有三条，都是硬约束：

1. **同一个对话无论调用多少次，都是同一个身份**。所以你能收到上一次发的消息
   的回执，别人也能认得出"还是那个它"。
2. **换协议身份 = 注册中心眼里的另一个人**。好友关系、群成员资格、对端固定
   的公钥全部失联。所以别名随便改，`agent_name` 冻结。
3. **不存在"一个 Agent 的多个对话共享一个身份"**。那不是简化，是把
   "谁说的"这个问题彻底搞乱——审计链上会出现同一个 actor 在不同上下文里
   说互相矛盾的话，而事后无法分辨是哪个人格说的。

如果你确实想让几个对话在别人看来是"同一个团队"，用**标签**，不要共用身份。

---

## 三、两级寻址：别名与标签

两者的区别是本轮设计的核心，混用会直接导致发错人。

| | 别名（label） | 标签（tag） |
|---|---|---|
| 数量 | 一台机器上**唯一** | 多个会话可共享 |
| 语义 | "这个对话叫什么名字" | "这个对话擅长/负责什么" |
| 示例 | `@运维`、`@写手` | `值班`、`数据库`、`前端` |
| 按它找 | 一定命中一个 | 可能命中多个 → 报歧义 |
| 能改吗 | 能，随时 | 能，随时 |
| 进协议吗 | 不进（纯本地） | 不进（纯本地） |

**为什么要两个而不是一个：**

只有一个名字时，你会被迫起出 `运维1` `运维2` `运维-数据库` 这种名字——那其实
是在用命名字段硬塞分类信息。而人真正想说的是"找个懂数据库的人问一下"，
这时他要的是**按属性找人**，不是背名字。

**为什么按标签命中多个必须报错：**

```
$ a2alink say 值班 "MySQL 主从延迟 30s"
❌ 标签 '值班' 有 2 个会话在用（@写手、@运维），请改用具体别名或会话 ID。
```

系统知道有两个候选，但它不知道**这一次**该找谁——那是业务判断，不是寻址问题。
瞎挑一个（哪怕是"最近活跃的"）的后果是：任务发给了错的人，两边都觉得自己没错，
而真正该做这件事的人从头到尾不知道有这回事。

**歧义不猜，这是设计，不是偷懒。**

## 四、匹配顺序

`a2alink say <目标>` 里的目标按下面顺序解析，命中即停：

```
1. 完整会话 ID         sess-ops-0001         最精确
2. 别名               @运维 / 运维            唯一名字，语义最强
3. 标签               数据库                 共享属性，多命中则报歧义
4. 会话 ID 前缀        sess-wri               弱匹配，必须唯一
5. 交给协议           远端 agent 名 / agent_id 都不在本机会话表里时
```

为什么标签排在 ID 前缀前面：人说"发给值班的"时，脑子里想的是**人**；
说"发给 sess-3f2a"时想的是**编号**。前者更常见，优先级就该更高。

为什么完整 ID 排第一：它是唯一没有歧义空间的写法，排查问题时应该有一条
"绝对不会有歧义"的路可走。

## 五、怎么知道该发给谁：发现

名字是本地知识，注册中心不知道"运维"是谁（也**不应该**知道——那会把
组织结构和人员分工泄露给中继）。所以发现分两层：

### 5.1 本机：`a2alink peers`

```
本机对话（3 个）
 → @运维      s-sessops000  最后活跃 刚刚        [值班,数据库]
   @写手      s-sesswri000  最后活跃 12 分钟前   [值班,文档]
   (未命名)    s-a1b2c3d4e5  最后活跃 3 小时前

中继上的其它 Agent（2 个，不在本机会话表里）
  · s-9f8e7d6c5b    caps=code-review
  · s-1122334455    caps=-
```

这一屏就是"我该发给谁"的答案。它同时给出三个线索：**叫什么**（别名）、
**擅长什么**（标签）、**还活着吗**（最后活跃）。

最后活跃这一列容易被低估：给一个三天没动过的对话发紧急任务，等于把信投进
一个没人住的信箱。`check` 能收到是运气，不是机制保证。

### 5.2 跨机：`a2alink discover`

远端只知道 `name` 和 `capabilities`，不知道你的本地别名和标签。
跨机时用 `--cap` 按能力筛选，再挑一个加好友。

**能力和标签不是一回事，别混：**
- `capabilities` 会同步到注册中心，别人能看到，用于**跨机发现**，所以只写
  不含组织信息的能力（`code-review`、`sql`）。
- `tags` 只在本机，用于**本机寻址**，可以写内部叫法（`值班`、`二组`、
  `那个跑批的`）。

把内部叫法写进 capabilities 等于把组织结构发到中继上——这是本项目的
出站红线之一，`discover` 里也刻意不返回 `owner` 字段。

## 六、多 Agent 协作的三种拓扑

寻址问题在不同拓扑下的难度完全不同。选错拓扑，再好的寻址也救不回来。

### 6.1 点对点（1 对 1 派活）

```
A ──"帮我看下 502"──> B
```

最简单，也最可靠。**要求的是一条稳定关系**：双向好友（跨机）或同机会话
（`local_mesh`）。适合明确的"我做不了，你来做"。

### 6.2 值班池（同标签多人，谁空谁接）

```
        ┌──> 值班甲
派单 ───┼──> 值班乙
        └──> 值班丙
```

这是标签唯一的正当用法：**人挑，不是系统挑**。a2alink 只负责告诉你
"有三个值班的"，不负责替你分配。真要做自动分配，那是调度器的事，
而且必须解决"谁认领"的并发问题——本项目没有做，因为一个做错的自动分配
比手动慢一点危险得多。

### 6.3 群（多对多，需要共识）

```
A ─┐
B ─┼──> 群 grp-xxx ──> 全员
C ─┘
```

群解决的是"同一件事需要多人同步"，不是"找人干活"。群的表决模型
（`unan` 全员同意 / `any` 一票否决 / `major` 多数）在 `docs/abuse.md` 里，
其中最重要的一条判断是：**全员同意不能当默认**——成员离群会让表决永久死锁。

**不建议**用群来派任务：任务需要明确的负责人，而群消息天然不指定负责人。
"发到群里了"在事后等于"没有人负责"。

## 七、常见错误

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| `找不到名为 s-xxxx 的 Agent` | 会话只在本地登记过，没在注册中心上线 | 跑一次 `a2alink session name <名字>` 或任意 `check` |
| `标签 X 有 N 个会话在用` | 标签本来就可共享 | 用别名，或先 `session tag` 收敛标签 |
| 消息发出去了，对方几小时才回 | 对方 Agent 没被唤起 | 正常。要快要让对方挂轮询进程，见第一节 |
| 换了个对话窗口，收不到之前的消息 | 消息是投给**那个身份**的，不是投给人 | 用 `session list` 找到原对话，或在那边 `check` |
| 改了名之后好友关系没了 | 改的是协议身份而不是别名 | 只能重新加好友。所以 `session name` 只改别名，不动身份 |

---

## 八、一句话总结

**寻址的本质不是"找到一台机器"，是"找到愿意为这件事负责的那个身份"。**

所以本项目宁可让你多敲一次别名，也不替你猜；宁可告诉你"有两个候选"，
也不按"最近活跃"替你分配责任。责任一旦被系统悄悄分配，就没人认了。
