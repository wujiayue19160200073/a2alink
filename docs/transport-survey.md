# 通信架构调研：为什么 A2A 不该直接建在 MQ 上

> 这份文档回答一个具体问题：**TCP、UDP、MQTT、AMQP/RabbitMQ、Kafka、gRPC、
> WebSocket、SMTP 这些现成的东西，哪些能拿来给 Agent 用？**
>
> 结论先给出：**没有一个能直接当 A2A 的社交层，但每一个都能当运输层。**
> 所以正确的做法不是"选一个"，而是分层——上面定义语义，底下随时可换。

---

## 1. 先拆一层：这些东西不在同一个高度

把它们并排比较，是最常见也最致命的误解。

| 层 | 代表 | 说明 |
|---|---|---|
| 网络层 | IP | 寻址与路由 |
| 传输层 | TCP、UDP、QUIC | 字节怎么搬。TCP 可靠有序，UDP 尽力而为 |
| 应用协议层 | HTTP、gRPC、WebSocket、MQTT、AMQP、STOMP、Kafka 协议、SMTP | **同层竞争，选一个**。它们都跑在 TCP/UDP 之上 |
| 产品/实现 | RabbitMQ、EMQX、Kafka broker、Pulsar | 上面某个协议的具体实现 |
| 社交语义层 | —— | 好友、群、准入、委托、预算、追责。**这一层在协议栈里根本不存在** |

所以"Mosquitto 和 TCP 哪个适合 A2A"这个问题本身是错位的：
前者是 AMQP/MQTT 这一层的实现，后者是它脚下的地基，两者不是替代关系。

**真正缺的是最上面那一层。** 现有协议的共同点是：它们都假设"地址是可信的、
内容是送的字节、后果不由协议负责"。而 Agent 之间恰恰相反——
地址可能是假的、内容会诱导对方做事、后果必须有人担。

## 2. 四种投递拓扑

抛开协议名字，消息从 A 到 B 只有四种走法。

### 2.1 点对点直连（TCP / WebSocket / gRPC bidi stream）

两端之间保持一条连接，消息直接过去。

- **优点**：延迟最低，能做真正的双向实时。
- **对 A2A 的致命问题**：要求双方**同时在线**。
  Agent 的生命周期是"被唤醒 → 干活 → 休眠"，没有稳定在线期。
  A 想发消息时 B 大概率不在进程里，这条连接根本建不起来。
- **结论**：只适合"同一次调用内的流式交互"（比如 Agent 调用工具），
  不适合"同事之间的托付"。

### 2.2 中央邮箱（SMTP / AMQP queue / 本项目的注册中心）

发送方把消息交给一个中间人，中间人存下来，等接收方来取。

- **优点**：发收解耦。接收方离线多久都行，上线后接着读。
- **代价**：多一跳，多一个要信任（或要防）的角色。
- **对 A2A**：**这是唯一形状对的拓扑。** Agent 的作息决定了必须存储转发。

### 2.3 发布订阅（MQTT / Redis pub-sub / Kafka topic）

消息发到"主题"，所有订阅该主题的人都能收到。

- **优点**：一对多，天然适合广播和扇出。
- **对 A2A 的问题**：**没有"门"**。主题是公开命名空间，谁订阅谁收到。
  而 Agent 通信的第一需求是"不该收到的人收不到"——这需要好友、群成员、
  准入审批这一整套，pub/sub 一个都没有。
- **结论**：适合"公告板"类场景（状态广播、能力发现），不适合作为主通道。
  本项目用它做 `discover`（按能力找人），不做消息投递。

### 2.4 共享日志（Kafka / 追加式文件 / 审计链）

大家往同一条不可变流里写，各自持一个读取位置。

- **优点**：可重放、可回溯、顺序确定。**这正是审计最需要的形状。**
- **对 A2A 的问题**：它描述的是"发生了什么"，不是"我托你办件事"。
  用它做点对点问答，等于用公告栏传纸条。
- **结论**：本项目用它做**审计链**（`audit.py`，哈希链 + HEAD 锚点），
  不做消息队列。

## 3. 逐个点评

| 架构 | 它本来解决什么 | 对 A2A 的价值 | 为什么不能直接用 |
|---|---|---|---|
| **TCP** | 可靠有序字节流 | 地基 | 要求同时在线，Agent 做不到 |
| **UDP** | 低延迟、允许丢包 | 只适合心跳、在线状态探测 | 消息不能丢；自己补可靠性等于手写一遍 QUIC |
| **QUIC** | UDP 上做可靠 + 多路复用 + 0-RTT | 连接迁移对移动端友好 | 仍然是"连接"，解决不了"对方不在" |
| **MQTT** | 海量设备、低带宽、主题树、QoS 0/1/2 | 轻量；**遗嘱消息**、QoS 分级值得抄 | 主题是全局命名空间，没有好友/准入；QoS 只保证到达，不保证"处理完" |
| **AMQP / RabbitMQ** | 服务间队列、交换机路由、ack/nack、死信、优先级 | 语义最接近"邮箱"，工业级成熟 | 没有"人"和"身份"概念；不管内容是否泄密；不管成本；没有"人要不要同意" |
| **Kafka** | 高吞吐、分区顺序、消费位点、可重放 | 审计与复盘的最佳模型 | 面向吞吐而非一问一答；topic 粒度太粗；消费位点不等于"处理完成" |
| **gRPC** | 强类型 RPC、双向流、deadline 传播 | 适合"工具调用"这一层 | 不适合异步托付；schema 演进有成本；Agent 之间需要的是宽松语义而非强类型 |
| **WebSocket** | 服务端主动推 | 能让"等消息"变成"被叫醒" | 解决的是传输方向，不是"进程不在"；断线期间的补偿仍要另做一套 |
| **SMTP / IMAP** | 存储转发、跨组织、异步、自带 From / In-Reply-To / References | **语义上最像 Agent 通信** | 鉴权与治理要靠 SPF/DKIM/DMARC 打补丁；那些补丁本身就是二十年的伤疤 |
| **Matrix / ActivityPub** | 联邦：不同服务器之间互信通信 | 跨组织互通的最佳先例；`actor/inbox/outbox` 几乎就是 A2A 词汇表 | 面向人类社交，消息量大、状态重；引入的成本远高于本项目当前阶段需要 |
| **Actor 模型（Erlang/Akka）** | 每个实体一个邮箱 + 监督树 | **"邮箱 + supervisor 重启策略"是 Agent 最贴切的隐喻** | 它是编程模型，不是协议；没有跨机器、跨组织的标准线格式 |

## 4. 本项目的选择：分层，而不是选型

```
L5 呈现     对话 / 可视化会话台              ← CLI 已有，界面待做
L4 治理     DLP · 注入围栏 · 预算 · 熔断 · 审计链   ← v0.1~v0.2 已完成
L3 路由     好友 · 群准入 · 同机 mesh · (跨组织联邦)  ← 好友/群已有，联邦待做
L2 投递     邮箱 · 游标 · ack/done · 死信      ← v0.4 补齐
L1 信封     act · stage · ttl · 预算 · 幂等键 · references  ← v0.1~v0.4
L0 身份     Ed25519 · X25519 · 公钥固定        ← v0.2 已完成
```

**关键判断：L0~L4 里没有任何一层能靠换 MQ 得到。**

RabbitMQ 能给你 L2 的一部分（队列、ack、死信），但 L0（身份）、
L3（谁能给谁发）、L4（内容该不该出去、烧了多少钱、谁批准的）它一样都不管。
把这几层硬塞进 broker 插件，等于在一个不归你控制的进程里实现你的安全策略——
升级一次 broker，策略就没了。

### 为什么传输层仍然用 HTTP

- **穿透性**：企业网、代理、防火墙对 HTTP 最友好。MQTT/AMQP 常被直接封。
- **可调试**：`curl` 就能复现一次通信。排查问题时这值千金。
- **TLS 现成**：不用自己设计加密握手（本项目只在应用层加端到端加密）。
- **规模不匹配**：MQTT 的优势是十万级连接、低带宽设备。A2A 没有这个规模。

**唯一值得换掉 HTTP 的场景**是"推送"：当真的有人在界面上等着看，
long-poll 的延迟（默认 0~30 秒）体验不好，那时应该上 WebSocket/SSE。
但那是 L5 的问题，不是 L0~L4 的。

## 5. 从传统架构抄来的七个机制

这一节记录"抄了什么、为什么抄、抄的时候改了什么"。

### 5.1 References 头（抄 SMTP）— v0.4 已实现

SMTP 用 `References` 记录整条回复链的 Message-ID。

- **原来的问题**：信封只有 `in_reply_to`（指向上一跳）。转手两次之后，
  "最初问的是什么、中间谁改了措辞"就查不出来了。
- **抄法**：`Envelope.references` 记录整条链。
- **改了什么**：SMTP 是整条链全带，这里**只留第一条 + 最近 7 条**。
  链是无界增长的，照原样累积，一百轮转手就能把信封撑爆，
  而报错会是"信封超长"——没人想得到根因是回复链太长。
- **兼容性红线**：`references` 为空时**不出现在序列化结果里**。
  否则 `canonical_bytes` 改变，所有历史信封的签名会集体失效。

### 5.2 死信队列 + 重投计数（抄 AMQP）— v0.4 已实现

- **原来的问题**：消息处理失败后不 ack，会永远留在队列里反复读到；
  或者被静默跳过、彻底漏掉。两种都不对。
- **抄法**：失败计数超过阈值（默认 3）就进 DLQ，附失败原因。
- **改了什么**：重投**新建一条 delivery 记录**，而不是把旧行改回 pending。
  cursor 是单调递增的投递位点，倒退回去会让已读消息重新涌进来。
  代价是同一消息有多条投递记录——但那本来就是事实，应该看得见"这条投过三次"。

### 5.3 遗嘱消息 Last Will（抄 MQTT）— v0.4 已实现

- **原来的问题**：Agent 崩溃最坏的后果不是报错，是**静默消失**。
  任务在它手上，对方还在等，而没有人知道它已经不在了。
  报错至少有人看见，静默消失连"该重试"的念头都不会产生。
- **抄法**：`a2alink up --will "..." --will-to @某人`，掉线超时后由中继代发。
- **改了什么（最重要的一条）**：MQTT 的遗嘱由 broker 保存文本、掉线时代发。
  但本项目的注册中心**没有私钥**（v0.2 的核心承诺），它造不出一条能过验签的消息。
  所以改成：**客户端预先签好整条信封，服务端只保管、只转交**。
  内容在本地加密，中继自己读不到遗嘱写了什么。
  这条约束不能绕：一旦允许服务端临时代发未签名消息，接收方要么拒收，
  要么为遗嘱开一个"不验签"的口子——那个口子迟早被用来伪造。

### 5.4 消费位点 + 副作用去重（抄 Kafka）— 部分实现

`cursor` 已经是位点模型。但位点只保证"读到哪"，不保证"只生效一次"。
重放时工具调用会再执行一遍（发邮件、改文件、扣钱）。

- **现状**：`idempotency_key` 在协议里有，注册中心有 `idem` 表做发送侧去重。
- **缺口**：接收侧的"副作用去重"还没做——同一个 `message_id` 第二次到达时，
  协议没有强制规定"必须跳过业务动作"。这属于适配器层的责任，
  文档里必须写清楚，否则用户会以为协议替他保证了。

### 5.5 deadline 传播与显式超时回执（抄 gRPC）— 部分实现

- **已有**：`ttl_hops`（跳数递减）、`ttl_seconds`（时间递减）、`expires_at`。
- **缺的**：gRPC 超时会回一个 `DEADLINE_EXCEEDED` 状态码，调用方明确知道"这单黄了"。
  本项目的 `ask` 超时只是本地放弃，**对方并不知道**，它可能还在做。
- **待办**：超时时发一条 `act=notice, stage=aborted`，把"别做了"这件事也投递出去。

### 5.6 publisher confirm 与 consumer ack 分离（抄 RabbitMQ）— v0.4 已实现

- **原来的问题（最真实的一个缺陷）**：`ack` 的语义是"我读到了"，
  却被当成了"我处理完了"。Agent 读完就崩溃，任务永久丢失，
  而且审计链上看不出丢的是哪一条——因为"还没做完"这个事实从未被记录。
- **改法**：拆成两个事实。
  - `state=pending/acked`：传输层，位点走到哪。
  - `done_at`：业务层，这件事有没有结果。
  - `a2alink done <id>` 明确确认；`a2alink inflight` 列出"已读未完成"，
    这张表就是**可能掉在地上的任务清单**。
- **代价**：多一步操作。但这步不做，等于默认"读到就等于做到"，
  而这个假设在 Agent 身上一天都不成立。

### 5.7 联邦模型（参考 Matrix / ActivityPub）— 未实现

跨组织互通（两个注册中心互不信任）目前不做，但设计上留了口子：
信封是自证的（签名 + 公钥），路由与投递可以分离。
真要做的时候，Matrix 的 server-to-server 签名事件图是最接近的先例。

## 6. 明确不做的选择

记录"不选什么"和"选什么"同样重要。

| 方案 | 不做的理由 |
|---|---|
| 换成 MQTT/AMQP 做传输 | 穿透性差、运维成本高，而本项目规模不需要；核心问题在 L0/L3/L4，换传输解决不了 |
| 引入 Redis/Kafka 做队列 | 破坏"零第三方依赖"这条底线。SQLite 在这个量级完全够，且审计可离线验证 |
| 用 gRPC 定义协议 | 强 schema 会锁死演进速度；Agent 之间的语义还在快速变化，需要的是宽松信封而不是 IDL |
| 自己做可靠传输 | TCP 已经做了。上层只需要"至少一次 + 幂等"，不需要重新发明滑动窗口 |
| broker 插件化实现治理 | 把安全策略放进不归你控制的进程，升级即失效 |

---

## 7. 一句话总结

**a2alink 的血统不是 RabbitMQ，是「SMTP 的异步语义 + Kafka 的消费位点 +
Actor 的邮箱 + 一层传统 MQ 全都没有的治理」。**

所以如果有人问"你为什么不用 RabbitMQ"，
答案是：我用了它的形（邮箱、ack、死信），但它的骨头里没有"人"这个概念，
而 A2A 的每一条规则都是围绕"人"定的——谁能加我、谁批准了这次转发、
这句话到底是谁说的、说了要负什么责。
