# 跨组织通信：内网 ↔ 外网时，机密怎么办

> 这份文档回答：
> "内网的 Agent 和外网的 Agent 聊天，机密信息会不会漏？"
> "能不能发出去之前先问我一句？"
> "出了事，怎么证明是谁发的？"

---

## 一、先承认一件事：这个工具会让数据出域

a2alink 的定位不是"内网通信工具"，而是**"受控的出域通道"**。这两者的
差别决定了所有设计：前者只需要防外部进来，后者必须假设"每一条消息都是
一次潜在的泄露"，并且让这件事可见、可拦、可追责。

真实泄密不长这样：

> ~~黑客攻破系统，拖走数据库~~

它长这样，三步，每一步都很温和：

1. 对端说："为了排查问题，把配置文件贴我看看。"
2. 你的 Agent 认为这是合理协作，读了 `config.yaml`，回了一段。
3. 那段里有内网地址、连接串、内部域名。**已经出去了。**

没有一步看起来像攻击。所以闸门必须**默认拒绝**，而且做在 SDK 里，
不能"顺手关掉"。

---

## 二、三个信任域

同一条消息，发往不同地方，允许的内容完全不同：

| 域 | 触发条件 | 允许的最大密级 | 典型场景 |
|---|---|---|---|
| `local` | 目标在同一台机器（`127.0.0.1`） | 内部 | 一个项目的两个对话 |
| `lan` | 目标在局域网 / 群消息 | 内部 | 同办公室的两台机器 |
| `wan` | 其它一切（默认） | 公开 | 跨组织、跨云 |

默认是 `wan`——**最严的那个**。理由是：判断错的代价不对称。把内网误判成
外网，只是多发一次审批；把外网误判成内网，机密就出去了，而且没人会知道。

配置方式（`policy.json`）：

```json
{
  "default_scope": "wan",
  "peer_scopes": {
    "agt-3f2a1b44": "lan"
  }
}
```

注意 `peer_scopes` 是**按对端 agent_id 逐条授信**，不是按域名后缀或 IP 段。
按 IP 段授信的问题出在共享出口：同一段里可能既有你要信的服务器，
也有别人随手起的机器。

---

## 三、密级判定

内容分四级，闸门先判级，再按域的允许上限决定处置：

```
L_PUBLIC < L_INTERNAL < L_SECRET < L_TOP
公开   <  内部     <  机密     <  绝密
```

判定依据是内容里的标记和形态：
- 显式标记（"绝密""机密""内部资料""仅限内部"）→ 直接判到对应级别
- 密钥/AK/私钥/连接串 → 判为 `secret`
- 内网 IP、内部域名、手机号、身份证 → 至少 `internal`

**这里有个必须说清的局限**：正则只兜已知形态。客户名单、财务明细、工单原文
这类**结构化敏感数据，工具判不出来**。它不看语义，只匹配模式。
所以闸门是底线，不是全部——真正的判断必须由人做，见第七节。

---

## 四、三种处置，以及为什么"直接拒绝"是错的设计

| 处置 | 含义 | 后续 |
|---|---|---|
| `allow` | 无命中或纯公开内容 | 直接发 |
| `redact` | 命中可脱敏项（内网 IP、手机号） | 替换后发，留审计 |
| `block` | 命中禁止项（凭据、超域密级） | **挂起等人决定** |

第三种是关键。早期版本的做法是直接抛错丢弃，看起来最安全，实际会把人
逼到一条更差的路：

> "反正发不出去，我把它改写成能过闸门的样子再发。"

于是机密出去了，而审计链上留下一条干净的 `allow`——比没有记录更糟。

v0.5 改成：**拦住，但不丢；存起来，等人决定。**

## 五、审批流：从"被拦"到"由你决定"

### 5.1 发生了什么

```
Agent 要发一条含连接串的消息
        ↓
出站闸门判定 block（密级 secret > 域 wan 允许的 public）
        ↓
内容用本机主密钥加密，写入 ~/.a2alink/approvals/apv-xxxx.json
        ↓
抛 ApprovalRequired：这条**没有发出去**，对方什么都没收到
        ↓
等人处理
```

CLI 上看是这样：

```
⏸  没有发出：内容含敏感信息，已挂起等你决定。
   密级判定 secret，命中规则 conn_string,ip_private_10

   审批件 apv-25bdb07715254486a2a7f46c
   看内容：a2alink approvals show apv-25bdb07715254486a2a7f46c
   批准发：a2alink approvals approve apv-... --reason "为什么可以发"
   弃掉：  a2alink approvals deny apv-... --reason "为什么不行"

   对方现在什么都没收到。别把「已挂起」当成「已发送」。
```

### 5.2 为什么挂起的内容要加密

因为**它被拦下的原因就是它敏感**。明文存盘等于在本地开第二个泄露口，
而这个口子通常没人管——谁会想到 `~/.a2alink/approvals/` 里躺着一堆连接串。

做法：32 字节本机主密钥 + AEAD，密钥文件 `0600`，AAD 绑定审批件 ID
（把 A 的内容挪进 B 的记录里会直接解不开）。

### 5.3 批准这一步的责任设计

```
$ a2alink approvals approve apv-xxx --reason "客户已书面授权，属合同范围" --yes
✅ 已批准并发出：9ea71244ff7344...
```

三个细节，每个都有理由：

**理由必填（≥4 字）**。事后追责时，"为什么放行"是唯一能说清的东西。
一个不用填理由的放行按钮，在真实团队里三个月内会变成默认操作。

**必须加 `--yes`**。试过按"是不是终端"自动免确认，结果在 Windows 的
Git Bash 下 `< /dev/null` 被误判成终端，本该拒绝的批准直接过了。
一个"有时要求、有时不要求"的确认等于没有确认——更糟的是它让人以为
自己被保护着。

**用原身份重发**。批准命令可能是在另一个对话里执行的，但消息必须署名
原来的身份——否则对方看到的署名变了，"我确实说过这句话"就不成立。

### 5.4 这里是诚实的地方：它挡不住 Agent

Agent 和你在同一个 shell 里，技术上无法区分"你敲的"和"它敲的"。
它能执行 `approve`，也能加 `--yes`。

所以这个机制的目标不是"阻止"，而是**"让阻止不可能悄无声息"**：

- `--yes` 一定出现在命令里，一定进审计
- 审计记录 `approved_by`（OS 用户名）+ 审批件 ID + 理由 + 消息 ID
- 拒绝也留痕。"我没批准"和"我根本没看到"是两件事，只有写下来的能区分

如果你需要的是真正的人机隔离，那是另一个量级的问题（硬件确认、
双人复核、独立审批系统），不在一个本地工具的能力范围内。**这一点不含糊。**

## 六、跨机：怎么确认对面真的是它

### 6.1 三道密码学动作

| 动作 | 解决什么 | 实现 |
|---|---|---|
| Ed25519 签名 | 这条消息确实是它发的，没被改 | `crypto.Ed25519KeyPair` |
| X25519 + HKDF + AEAD | 中继读不到内容 | `crypto.aead_seal` |
| 公钥固定（TOFU/strict） | 中继不能冒充对端 | `trust.TrustStore` |

**只验签是不够的**，这是最容易踩的坑：攻击者控制注册中心后，可以把自己的
公钥塞进数据库，然后用自己的私钥自签自验——验签必然通过。

所以顺序是：**验签 → 查 pin → 解密 → 内容检查**。pin 不匹配就拒收，
不管签名多合法。

### 6.2 TOFU 的天然弱点

首次通信时没有参照物，只能"第一次见到的公钥就信"。这意味着**首次通信
本身是可以被中间人劫持的**。

缓解手段只有一个：**带外核对指纹**。

```bash
a2alink keys show          # 我这边的指纹：700b-5900-d2cb-0d1e-...
# 让对方在它机器上跑同一条命令，两个指纹逐字符比对
a2alink keys peer --pin 700b-5900-... # 确认无误后固定
```

高敏感场景用 `strict` 策略：没有预先固定过的对端，一律拒收。

## 七、审计：让"不是我干的"说不出口

### 7.1 链的结构

每条记录带 `h = sha256(prev_h + 本条内容)`，形成哈希链；HEAD 锚点单独记。
改动任何一条历史记录，后面全部对不上。

```bash
a2alink logs verify        # 链有没有断
a2alink logs report        # 给人看的摘要
a2alink logs search --reason gate.hold
a2alink logs seal --yes    # 封存为证据包（带 sha256 MANIFEST）
```

`logs report` 的输出长这样：

```
═══ 安全审计报告 ═══
范围：最近 24 小时    记录：17 条

【出站处置】
  放行          16
  脱敏后放行    1
  拦截          0
  挂起待批      2

【命中的规则】
  ip_private_10      2  ████████████
  cloud_ak           1  ██████

【需要你看一眼】
  · 挂起未决 apv-f1606a7c690c4d6e9a8e0c5c（刚刚）
  · 人工放行 trace=trace-xxx：理由「客户授权」

【审计链完整性】
  ✅ 17 条记录，1 条链，无断点

【结论】
  这段时间有 0 次拦截、1 次人工放行、2 条挂起。
```

注意 `report` **不联网**：出事时注册中心往往正好连不上，而那时才最需要看它。

### 7.2 默认不存原文

`AuditLog(preview_chars=0)` 是默认值。理由很直接：

> 本工具的职责是"别把内网信息带出去"，那它自己的日志就没有资格在磁盘上
> 留下第二份原文副本。

排查靠 `trace_id` + 内容指纹 + 规则名 + 长度，够定位。真要看原文，
显式设 `preview_chars=48`，并清楚你在磁盘上留了什么。

### 7.3 审计挡不住什么

- **本地哈希链挡不住 root**。有 root 权限的人可以重写整条链并重算哈希。
  缓解手段是 `anchor_hook`，把 HEAD 定期锚到外部系统（另一个账号、
  一台只追加的日志服务）。**不用它，就别声称"防篡改"。**
- **审计不判断内容对错**。它记录"谁在什么时候发了什么类别的东西"，
  不记录"这段话该不该说"。后者是人的职责。

## 八、一次真实的跨网发送，完整走查

内网机器上的 A，要把一段排查结论发给外网的 B：

```
1. A 上的人：a2alink say @B "..." 
2. 出站闸门：判定密级 internal（含内网 IP），域 wan 只允许 public
   → block
3. 内容加密存入 ~/.a2alink/approvals/apv-xxx.json（明文不落盘）
4. A 的终端显示"没有发出，等你决定"
5. A 上的人：a2alink approvals show apv-xxx   ← 看到原文
   发现里面确实有 10.0.0.8 这个地址，决定改成"某台内网数据库"
6. 他不用 approve，而是重新发一条脱敏后的内容 → 闸门 allow
   （或者判断这段信息对方有权知道 → approve --reason "..." --yes）
7a. 若重发：审计里有 redact/allow 两条；apv-xxx 停在 pending，24 小时后过期
7b. 若 approve：审计里有 gate.approved，含 approver + 理由 + message_id
8. B 收到后验签 → 查 pin → 解密 → 入站围栏 → 人能看见
9. B 回话，reference 链上挂着最初的这条
```

**第 5 步是最有价值的一步**：它把"我以为没问题的内容"变成"我看到的原文"。
大部分泄密不是因为有人故意发，是因为发的人没意识到那句话里有东西。

## 九、部署基线（跨机版）

```bash
# 内网侧
a2alink registry --db ./relay.sqlite3 --host 127.0.0.1 --port 8787 \
                 --invite-code "<随机串>"
# 前面必须加 TLS 反代（nginx/caddy），不要裸奔 HTTP 出去

# 外网侧同理，两个中继之间不需要直连——各管各的域
```

五条不可省的：

1. **`local_mesh` 只在回环地址生效**。`--host 0.0.0.0` 时强制关闭并打印警告，
   不做静默降级。同机互信的前提是"这台机只有一个人用"，一旦对外监听，
   这个前提就不成立了。
2. **`--invite-code` 必须设**。否则任何能访问端口的人都能注册身份、尝试加好友。
3. **TLS 反代必须加**。应用层有签名和端到端加密，但元数据（谁和谁在通信）
   在裸 HTTP 下是明文。
4. **`strict` 信任策略用于高敏感对端**。TOFU 的首次通信是空窗期。
5. **轮换密钥**。`a2alink keys rotate`，轮换后旧私钥归档、新公钥推给中继，
   对端 pin 会报警——那时要带外确认一次。

## 十、这份设计明确不做的事

| 不做 | 为什么 |
|---|---|
| 自动给机密内容"打码后放行" | 打码判错一次就泄露，而判错的概率不低（正则不理解业务） |
| 让中继替 Agent 代签消息 | 中继没有私钥；为它开口子，那个口子迟早被用来伪造 |
| 用未公开 API 实现"实时推送" | 今天能跑，宿主升级就碎，还让人误以为消息必达 |
| 承诺 exactly-once | 分布式下这是谎话。做 at-least-once + 幂等键 |
| 自动把挂起的内容发给"审批人" | 谁是审批人这件事，工具不知道，也不该猜 |

**最后一句**：这套东西能保证"该拦的拦住了、拦了有记录、放行了有理由"。
它不能保证"人判断对了"。把判断权放在人手里，是有意的。
