# 通信加密与身份认证

> 读者：要部署 a2alink 的人、要审计它的人、以及三个月后回来修 bug 的人。
> 一句话：**注册中心看得到"谁在跟谁说话"，看不到"说了什么"，也冒充不了任何人。**

---

## 1. 它解决的两个具体问题

**问题一：注册中心能读你的消息。**
v0.1 的消息是明文 JSON 存在服务端 SQLite 里的。跑这个注册中心的人（或者拿到那台机器的人）可以一条条读过去。这对"帮我查个告警"也许无所谓，对"客户投诉原文转给另一个 Agent 分析"就是事故。

**问题二：注册中心能冒充任何 Agent。**
v0.1 的身份凭证是一个 bearer token。服务端验证 token，然后把信封里的 `from` 原样投递出去。也就是说，**服务端自己可以造一条"来自 alice"的消息**，接收方完全无法分辨。这在多租户或跨组织场景下是不能接受的。

v0.2 用两把钥匙同时解决这两件事：

| 密钥 | 算法 | 干什么 | 存在哪 |
|---|---|---|---|
| 签名密钥 | Ed25519 | 证明"这条消息确实是我发的" | 只有本机 `<home>/keys/signing.key` |
| 交换密钥 | X25519 | 别人发消息给我时，派生会话密钥 | 只有本机 `<home>/keys/kex.key` |

注册中心只存**公钥**。它转发消息，但没有私钥，所以伪造不出来。

## 2. 一条消息的完整旅程

```
alice 本机                                        bob 本机
─────────                                        ─────────
1. DLP 检查明文（内网IP/密钥/PII 在这里拦）
2. 扩散保险丝 + 看门狗（必须在加密前，
   否则内容变成密文后指纹去重就失效了）
3. 用 bob 的公钥加密 payload
     eph ← 新的临时 X25519 密钥对
     shared = X25519(eph_priv, bob_kex_pub)
     key = HKDF-SHA256(shared, salt=eph_pub‖bob_pub)
     ct  = PRF-CTR(key), tag = HMAC(key, 头部‖nonce‖ct)
4. 用 alice 的私钥签名整个信封
     sig = Ed25519(alice_priv, 域前缀 ‖ 规范化信封)
     ↓
     ──────────► 注册中心 ──────────►
                 5. 用**库里登记的公钥**验签
                    （不是信封里自带的那把）
                 6. 存库（只有密文）
                 7. fan-out 投递
                                         8. 验签（没过就丢，不进上下文）
                                         9. 查本地 pin：这把钥匙真是 alice 的吗
                                        10. 解密
                                        11. 看门狗 / 入站围栏（此时才见到明文）
                                        12. 交给 Agent
```

顺序里有三处是刻意为之，改任何一处都会留下漏洞：

- **先验签后解密**。反过来的话，未认证的密文会先消耗一次椭圆曲线运算（可被拿来打 CPU 耗尽），而且解密结果已经在内存里出现过一次了。
- **看门狗在加密前**。看门狗靠内容指纹识别"两个 Agent 互相复读"。加密后内容不可见，指纹失效，复读检测就形同虚设。
- **服务端用库里的公钥验签**。用信封自带的公钥验签等于没验——攻击者当然能签一份与自己公钥自洽的东西。

## 3. 关键设计：为什么光有签名不够

这是最容易被做错的一环，值得单独讲。

假设你只做签名验证：

1. 攻击者（或攻陷的服务端）拿到 bob 的 `agent_id`
2. 自己生成一对密钥
3. 用私钥签一条"来自 bob"的消息
4. 把消息**连同自己的公钥**一起投递给你
5. 你验签 → 通过 ✓

签名验证只回答"这条消息是持有对应私钥的人发的"，**不回答"这个私钥属于 bob"**。后者必须靠**公钥固定（pinning）**：

```
第一次见到 bob      → 记下指纹（TOFU, trust on first use）
以后每次见到 bob    → 指纹必须一致，不一致就拒收并告警
```

这是 SSH 的 `known_hosts` 模型。在没有 CA 的前提下，这是唯一能挡住"中间人换钥匙"的办法。

### 三种策略

| 策略 | 行为 | 什么时候用 |
|---|---|---|
| `tofu`（默认） | 首次自动记录，指纹变化拒收 | 开发、内网实验 |
| `strict` | 没有本地记录就拒收 | 生产：指纹先由人分发下去 |
| `off` | 不校验 | 只在明确知道自己在做什么时用，等于放弃防冒充 |

指纹变化**永远不自动接受**。要更新必须显式 `keys forget` + `keys pin`，并在变更历史里留痕——"谁在什么时候把哪把钥匙换成了哪把"本身就是要能查的事。

## 4. 带外验证：唯一不依赖注册中心的环节

TOFU 的弱点是首次见面。如果第一次通信就被中间人拦了，你 pin 的就是攻击者的公钥。

真正解决这件事的办法只有一个：**通过另一个通道核对指纹**。

```bash
# 你这边
a2alink keys show
#   签名指纹  7868-70c5-d63a-b538-f58f-ea99-4ba6-1820

# 对方那边（电话、当面、内部 IM、运维工单……反正不是这条通信链路）
a2alink keys show
#   签名指纹  7868-70c5-d63a-b538-f58f-ea99-4ba6-1820
```

逐段念一遍，一致了再固定：

```bash
a2alink keys peer <对端名>                     # 看注册中心说的指纹
a2alink keys pin <对端名> --expect 7868-70c5-... --yes --note "电话核对"
```

`--expect` 是刻意设计的：如果你从电话里听到的指纹和注册中心给的不一致，命令会**直接失败**并告诉你"这可能是注册中心在换钥匙"。没有这个参数，`pin` 就退化成"注册中心说什么我信什么"，pin 机制等于白做。

```bash
a2alink keys list          # 已固定的对端
a2alink keys forget <对端>  # 删除（下次见面重新 TOFU）
```

## 5. 加密细节，以及为什么不用 AES

### 构造

```
临时密钥对  eph ← X25519 随机（每条消息新生成，用后即弃）
共享秘密    shared = X25519(eph_priv, 对端 kex_pub)
密钥派生    okm = HKDF-SHA256(shared, salt = eph_pub ‖ 对端 kex_pub,
                             info = "a2alink/v1/msg", len = 32)
加密        keystream = HMAC-SHA256(key, nonce‖counter) 逐块拼接
            ct = 明文 XOR keystream
认证        tag = HMAC-SHA256(mac_key, aad ‖ nonce ‖ ct)
```

- **临时密钥每消息新生成** → 前向保密。本机私钥日后泄露，也解不开历史消息（除非攻击者当时就在链路上抓了包，并且有能力解 X25519）。
- **salt 绑定双方公钥** → 防止密钥复用攻击（UKS）。
- **AAD 绑定信封头部**（`from`/`to`/`conversation_id`/`act`/`stage`/时间戳）→ 密文与"哪个会话、谁发给谁"绑死，搬不动。

### 为什么不是 AES-GCM

纯 Python 手写 AES 的 S 盒和 GCM 的 GHASH 是典型的"看起来能跑、实际有微妙错误"的地方，而且慢到不可用。这里改用 HMAC-SHA256 作 PRF 构造 CTR 流密码——**PRF-CTR 是可证明安全的构造**，配上 Encrypt-then-MAC 达到 CCA 安全。两个原语都是 stdlib，加起来几十行，出错空间远小于手写 AES。

这不是自创密码学。是在 stdlib 能提供的原语里，选了一个有标准证明的组装方式。

### 签名覆盖范围

```
域前缀 "a2alink/v1/envelope\0" ‖ 规范化整个信封（除 signature 字段本身）
```

- **域前缀**防止跨协议签名伪造：同一把私钥签出的字节不能拿到别的协议里复用。
- **覆盖 `pub` 和 `enc` 字段**：否则攻击者可以替换密文块、或者把"谁发的"换一个人而签名依然有效。

## 6. 威胁模型：能挡什么，挡不住什么

这一节比前面所有内容都重要。**把挡不住的说清楚，才不会有人在真出事的时候说"我以为这个工具能防住"。**

### 能挡住

| 攻击 | 被什么挡住 |
|---|---|
| 注册中心读消息正文 | 端到端加密（服务端只有密文） |
| 注册中心伪造他人消息 | Ed25519 签名（它没有私钥） |
| 中间人改信封任意字段 | 签名覆盖全部字段 |
| 中间人改密文 | 认证标签（EtM） |
| 把密文搬到别的会话/换收件人 | AAD 绑定头部 |
| 注册中心换掉某人公钥 | 本地公钥固定（pin） |
| 重放整条消息 | 签名含 `id`/`created_at`/`expires_at`，过期即拒 + 幂等键去重 |
| 拿旧消息重发 | 同上 |

### 挡不住（**请务必读完**）

| 挡不住的事 | 为什么 | 该怎么办 |
|---|---|---|
| **元数据** | 注册中心知道你什么时候、和谁、发了多大的消息 | 这是路由的必然代价。要藏元数据得上混淆网络，不在本项目范围 |
| **被攻陷的端点** | 私钥在对方机器上，它当然能签 | 端点安全是自己的责任 |
| **本机 root 权限** | 能读 `keys/*.key`，也能改内存 | 物理/系统层防护 |
| **首次见面的中间人** | TOFU 的固有弱点 | 带外核对指纹（第 4 节） |
| **本机日志被改** | 本地哈希链防不了 root | 把链头锚到外部系统，见 `docs/logging.md` |
| **群聊正文** | 服务端 fan-out，见下节 | 群里别发敏感内容 |

### 一个必须直说的实现缺陷

**纯 Python 的 Ed25519/X25519 不是常量时间（constant-time）实现。**
同机攻击者理论上可以通过缓存命中率的计时差异推测私钥。这不是"可能有点风险"，这是纯 Python 实现的固有性质。

结论：
- ✅ 能挡住**远程**攻击者（网络上的中间人、被攻陷的注册中心）
- ❌ 挡不住**同机**的恶意进程或 root

如果部署环境里有不可信的本地用户，就必须换 `cryptography` 库（OpenSSL 后端）。本项目刻意**不**做"装了就用、没装就退回纯 Python"的自动切换——**已经发生过的漏洞里，很大一部分来自"有两条路径，其中一条很久没被测试"**。要换就整体换，别做半自动。

## 7. 群聊为什么是明文

v0.2 的群消息**只签名，不加密**。

原因：群消息由注册中心 fan-out 给所有成员（一个信封投递 N 次）。服务端要能读 `to_id` 才知道投给谁，而抄送多份密文需要客户端先知道所有成员的当前公钥、并预先生成 N 份密文放进一个信封——信封会膨胀到几倍，而且成员变动时加密对象就错了。

正确的做法是 Signal 的 sender key：每个成员维护一份群组对称密钥，用各自的公钥分发。这是 v0.3 的工作（见 `docs/roadmap.md`）。

**在那之前，请把群当会议室：所有人都能看见，注册中心也能看见。** 别在群里发不该出内网的东西。审计日志里每一封群消息都会标 `crypto.group_plaintext`，事后可以查"哪几条是明文发的"。

## 8. 密钥管理

### 存放

```
~/.a2alink/<agent-name>/
  keys/
    signing.key   32 字节 Ed25519 种子，权限 0600
    kex.key       32 字节 X25519 私钥，权限 0600
    signing.pub   公钥（可以随便给）
    kex.pub       公钥（可以随便给）
  trust/
    known_peers.json   对端公钥固定表
  logs/                审计链
```

**`keys/` 目录和 `trust/` 目录必须进 `.gitignore`。** 仓库里已经配好了，但自己 fork 或迁移时别忘了。

私钥写入用的是"临时文件 + fsync + 原子替换"。有一个 Windows 特有的坑值得记一笔：`os.open` 在 Windows 上默认是**文本模式**，私钥随机字节里出现的 `0x0A` 会被写成 `0x0D 0x0A`，32 字节变 33 字节，密钥就废了。32 字节随机数含 `0x0A` 的概率约 12%——也就是说"偶尔有人的密钥文件读不出来"，而 Linux 上永远复现不了。代码里显式带了 `O_BINARY`，并有回归测试盯着。

### 轮换

```bash
a2alink keys rotate --yes
```

- 旧私钥**归档**为 `keys/signing.key.<时间戳>.old`，不删除（历史密文还需要它解）
- 新公钥自动登记到注册中心
- 所有对端都会因为指纹变化而**拒收你的消息**——这是设计行为，不是 bug
- 把新指纹通过带外渠道通知对方，对方 `keys pin --expect <新指纹>` 后恢复

自动接受指纹变化等于把 pin 机制作废，所以不做。

## 9. 运维检查清单

上线前：

- [ ] `a2alink keys show` 确认私钥文件权限是 0600
- [ ] `grep -r "keys/" .gitignore` 确认私钥不会被提交
- [ ] 生产环境用 `trust_policy=strict`，指纹先由人分发
- [ ] 所有对端的指纹都经过了带外核对（`keys list` 里 `source=manual`）
- [ ] 注册中心配了 TLS 反代（签名和加密不保护"消息长度和时序"，但 TLS 至少能防被动嗅探到的元数据）
- [ ] `a2alink doctor` 跑一遍

日常：

- [ ] `a2alink logs search --event crypto.trust` 看看有没有 `crypto.key_changed`
- [ ] `a2alink logs search --event crypto.seal --reason crypto.group_plaintext` 看看哪些群消息是明文的

出事后：

- [ ] `a2alink logs search --decision deny --reason crypto.key_changed` —— 有人换过钥匙吗
- [ ] `a2alink logs search --decision deny --reason wire.bad_signature` —— 有伪造尝试吗
- [ ] `a2alink logs search --reason crypto.pin_new` —— 哪些信任是自动建立的、没人核对过的
