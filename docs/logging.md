# 审计与排查：让每条放行都能追到人

> 这个文档解决一个很具体的问题：出事之后，怎么避免变成"谁都说不清"。

## 1. 先说三个最没用的句子

真实事故复盘里，最常出现、也最没价值的三句话是：

> "我记得我没让它发。"
> "日志里没记录，应该没发生过。"
> "可能是对方那边的问题。"

这三句之所以能说出口，是因为日志只记了一半：**只记"拦了什么"，不记"查过什么"**。
于是"我没发"和"系统没拦"之间永远有一段灰色地带，谁都可以站在对自己有利的那一侧。

本项目的做法是：**把每一次裁决都记下来，包括通过的裁决**。
你要证明的不是"我拦住了"，而是"我按某条规则检查过、当时的判定是这样"。
这两件事在合规审计里的分量完全不同。

---

## 2. 日志分成两层，回答两个不同问题

| 层 | 存在哪 | 回答什么 | 谁能改 |
|---|---|---|---|
| 结构化审计表 | SQLite `audit` 表 | 某段时间发生过什么，便于统计与检索 | 有库权限的人（可 UPDATE） |
| 哈希链日志 | `<home>/logs/audit.*.jsonl` | 这些记录有没有被动过手脚 | 改了就断链，检得出来 |
| 服务端投递表 | SQLite `messages` / `deliveries` | 消息投到了谁、成功没有 | 有库权限的人 |

**为什么同一个事件要写两处？**
数据库是"人可以 UPDATE 的东西"。一句 `UPDATE audit SET decision='allow' WHERE ...`
就能把一次拦截改成一次放行，而且事后从数据本身看不出任何异常。
哈希链的作用不是阻止修改（本地文件一样能改），而是**让"改过"这件事留下痕迹**。

这不是冗余，是两个不同的问题：数据库回答"发生了什么"，哈希链回答"记录可不可信"。

---

## 3. 一条记录的字段

```json
{
  "v": 1,
  "seq": 42,
  "ts": 1793707600.123456,
  "iso": "2026-11-02T23:41:53.120+08:00",
  "chain": "main",
  "trace": "trace-65573dd7a8c94e3d9a0cc0c8",
  "event": "gate.egress",
  "actor": "agent:agt-a2a4bbd8e65f4694883cf746",
  "decision": "deny",
  "reason": "egress.deny",
  "detail": { "peer": "agt-...", "rules": ["cloud_ak"], "level": "secret" },
  "evidence": { "sha256": "9f2c...", "bytes": 128 },
  "preview_fp": "3ab1...",
  "preview_len": 41,
  "prev": "上一条的 h",
  "h": "本条哈希"
}
```

几个字段的用意，值得单独说：

- **`reason` 必须来自枚举，不允许自由文本。**
  `REASONS` 里登记了 27 个理由码，写不在表里的值会直接抛 `AuditError`。
  这条限制是刻意的：自由文本一定会退化成"已处理""异常""待查"这类什么都没说的词，
  而这类词在定责时是零价值。机读的理由码才能统计、才能告警、才能对比。

- **`actor` 区分三类主体**：`agent:xxx`（Agent 自主决定）、`human:xxx`（人确认）、
  `service:registry`（系统行为）。责任划分靠的就是这个字段。

- **`evidence.sha256` + `preview_fp`**：不存内容原文，但存指纹。
  排查循环对话时，"这三条是不是同一段话"是最高频的问题，
  指纹就能回答，不需要把原文抄到磁盘上。

- **`preview` 默认关闭（`preview_chars=0`）。**
  这是本工具在立场上必须一致的地方：它的职责是"别把内网信息带出去"，
  那么它自己的日志就没有资格在磁盘上留第二份原文副本。
  真要看内容，显式 `audit_preview=48`，并清楚你留下了什么。

## 4. 理由码：能一眼看出谁在做事

| 理由码 | 含义 | 谁的责任 |
|---|---|---|
| `egress.deny` | 出站内容命中禁止项，已阻断 | 系统正常履职 |
| `egress.redact` | 命中可脱敏项，替换后放行 | 系统正常履职 |
| `egress.override` | **被拦了，但人强行放行** | **人** |
| `watchdog.deny` | 触发熔断（配额/预算/TTL/复读） | 系统正常履职 |
| `watchdog.override` | **熔断了，但人强行放行** | **人** |
| `propagation.deny_fanout` | 同一内容短时发往过多目标 | 系统正常履职 |
| `propagation.deny_forward` | 转发未开启，拒绝代他人传话 | 系统正常履职 |
| `ingress.quarantine` | 入站内容检出提示词注入，已隔离 | 系统正常履职 |
| `wire.dropped_malformed` | 信封畸形，丢弃 | 系统正常履职（但要查来源） |
| `wire.send_failed` | 提交注册中心失败 | 需区分：网络 / 被服务端拒 |
| `server.reject` | 服务端拒绝某请求 | 需看 `status` + `code` |

带 `.override` 的三个是**唯一会把责任从系统转到人身上的记录**，
所以它们同时也是唯一强制 `fsync` 的类别——必须真的落到磁盘上，不能停在页缓存里。

## 5. 哈希链是怎么算的，以及它挡不住什么

```
h = sha256( v, seq, ts, iso, chain, trace, event, actor,
            decision, reason, detail, evidence, preview_fp, ..., prev )
h 再作为下一条的 prev
```

改任意一条的内容、删掉中间一条、调换两条的顺序，链都会在断点处对不上。
另外单独维护一个 `HEAD.<chain>` 文件，记录"最后一条是第几号、哈希是多少"，
用来发现**尾部被截掉**（否则删掉最后几条是看不出来的）。

### 必须说清楚的局限

1. **本地哈希链挡不住"整份重写"。**
   拿到机器 root 的人可以把日志和 HEAD 一起重算一遍，链仍然自洽。
   要真正做到不可否认，必须把链头定期锚定到你控制之外的地方
   （另一台机器 / SIEM / 可信时间戳服务）。`AuditLog(anchor_hook=...)` 留了口子，
   但本项目不假装本地链等于不可否认。

2. **并发写会分链。**
   抢到 OS 文件锁的进程用 `main` 链，抢不到的用 `p<pid>` 链。
   分链是可验证的，混写不是。宁可多条各自完整的链，
   也不要一条"看起来很完整、实际验不过"的链——后者比没有日志更危险，
   因为它会让人误信。

3. **只覆盖本机。**
   注册中心看不到参与方的本地日志，也不该看。这是隐私边界，不是功能缺失。

## 6. 收到事故之后的四步（按顺序）

```bash
# 1. 先固定现场，确认日志本身没被改过
a2alink logs verify
#   ✅ 完整 → 可以当证据用
#   ❌ 有断链 → 停下来，别清理，按第 7 节处理

# 2. 看这段时间整体画像：谁放行了什么、谁被拦了
a2alink incident --hours 24

# 3. 挑出可疑的那条，摊开它的完整一生
a2alink trace trace-65573d        # 支持短 id 前缀，表格里复制出来就能查

# 4. 导出固定证据（导出之后就别再往这个目录写东西）
a2alink logs export --out case-20261102.jsonl --hours 168
a2alink logs seal --yes --as case-20261102
```

**为什么第 1 步是 verify 而不是查内容**：
如果日志本身不可信，后面所有推断都建在沙子上。
先证明"这份记录是真的"，再基于它做事，顺序不能反。

`trace` 会同时给出本地决策链和服务端投递记录。
如果服务端那段查不到，它会明说"现在问不到"，而不是静默跳过——
**"没有输出"和"没有发生"是两件事**，排查时把它们混起来是最常见的坑。

---

## 7. 发现链断了怎么办

链断 = 这份日志不能作为证据使用。不要试图"修好"它。

1. **立刻停止一切清理动作。** 包括 `purge_old`、`logs seal`、删容器。
2. 把整个 `logs/` 目录**只读复制**出来（保留原文件，别原地操作）。
3. 记录发现时间和发现人——这本身要进事故报告。
4. 用 `logs verify` 的输出（哪个文件、第几行、什么类型）定位断点。
5. 判断性质：
   - 断在 `tail_truncated`：可能是磁盘满、进程被杀、或人为删除；
   - 断在 `hash_mismatch` / `prev_mismatch`：内容被改过或顺序被调过；
   - 断在 `seq_gap`：中间有记录被删。
6. 如果日志同时被改过，**优先相信服务端**那份（它不在同一台机器上），
   两边对照往往能还原出被删掉的是什么。

## 8. 定责的边界：哪些是系统的锅，哪些不是

这一节是写给复盘用的，也是这个模块存在的真正理由。

**系统应当负责的：**
- 该拦的没拦（规则漏了、规则被关掉了）；
- 拦了但没记录（这正是本模块要消灭的情况）；
- 记录了但记录的字段不足以定位（比如只写"已处理"）；
- 审计被自动清理任务顺手删掉。

**系统不负责的：**
- 人用 `--force --reason` 放行的（责任在人，记录里有名字和时间）；
- 结构化业务数据出域（正则挡不住"我们下季度主推的那个型号"）；
- 对方 Agent 拿到内容之后怎么用；
- 语义层面的诱导与社工。

**刻意不做的一件事**：`purge_old()` **不删审计表**。
业务数据有留存期（存着是隐私负担），审计记录是责任链（删了就没法追责）。
两者如果共用同一个 `cutoff`，谁都可以把 `days` 设成 0.01，
然后"系统自动清理"就成了最省事的洗证据方式。
审计要收缩，只能由人显式 `logs seal`，而归档动作本身也会留下记录。

---

## 9. 隐私边界：谁能看到谁的日志

| 主体 | 能看 | 不能看 |
|---|---|---|
| 本机 Agent | 自己 `logs/` 下的全部记录 | 其他 Agent 的本地日志 |
| 注册中心 | 自己经手的消息元数据 + 服务端审计 | 参与方的本地决策记录 |
| 同一条 trace 的参与方 | 该 trace 的元数据与审计事件 | 其他人的 payload 正文 |
| 无关的第三方 | 什么都没有（`/v1/trace` 会返回 403） | — |

`/v1/trace/<id>` 只回元数据（谁发给谁、什么时候、投递状态），**不回 payload**。
查问题不需要把别人的正文再复制一遍，能少一处副本就少一处泄密面。

---

## 10. 不要做的事

- ❌ 不要为了让"报表好看"而调高 `preview_chars`。那等于在磁盘上开了第二份原文。
- ❌ 不要把 `logs/` 目录提交到 git（`.gitignore` 已排除，别手动加回来）。
- ❌ 不要在事故现场 `rm` 日志。要归档就 `seal`，`seal` 只移动不删除。
- ❌ 不要用"日志里没有"来论证"没有发生"。先看 `wire.dropped_malformed`
  和 `wire.send_failed`——**丢失本身也会被记录**，这正是它存在的意义。
- ❌ 不要把 `force_reason` 写成"需要发"、"业务要求"这种话。
  半年后看这条记录的人，只能靠这句话判断当时是不是合理。
